# Перед парой

Полноценная электронная очередь для одной учебной группы: Next.js + Supabase Postgres, развёртывание на Vercel. Данные действительно сохраняются в общей базе; демонстрационного режима в приложении нет.

## Что умеет сайт

- Вход по фамилии и имени без почты и пароля; устройство запоминается на 180 дней.
- Одна активная очередь на группу, название предмета, время пары и примечание.
- Запись в конец, своё место, выход и повторная запись в конец.
- Автообновление каждые 8 секунд, пока вкладка видна; при возвращении на вкладку — сразу.
- Админская сессия по секретной фразе на 12 часов.
- Перенос стрелками или на конкретное место; обмен двух участников.
- Ручное добавление, удаление, отметка первого как прошедшего.
- Закрытие и повторное открытие записи, завершение пары.
- История с постраничным просмотром; журнал действий для администратора.
- Адаптивный интерфейс, локальные шрифты с кириллицей, состояния потери соединения.

## 1. Создайте базу Supabase

1. Откройте [Supabase Dashboard](https://supabase.com/dashboard) и создайте новый проект на бесплатном тарифе. Выберите регион поближе к вашим пользователям.
2. Задайте пароль базы и дождитесь готовности проекта. Пароль базы **не является** секретной фразой администратора сайта и не нужен в настройках этого приложения.
3. Откройте **SQL Editor → New query**.
4. Откройте файл [`supabase/schema.sql`](supabase/schema.sql) в этом репозитории, скопируйте **весь** его текст, вставьте в SQL Editor и нажмите **Run**.
5. После успешного выполнения в схеме `public` появятся `members`, `queues`, `entries`, `audit_log`, `rate_limits` и три функции. Очереди и участники пока пустые — это нормально.
6. В **Project Settings → Data API** скопируйте **Project URL**, например `https://abcdefgh.supabase.co`. Это HTTPS-адрес проекта, а не строка `postgresql://...`. Data API должен быть включён, а `public` — находиться среди exposed schemas (обычно это уже настроено).
7. В **Project Settings → API Keys** создайте или скопируйте **Secret key** с префиксом `sb_secret_`. Нужен секретный серверный ключ, а не `sb_publishable_` и не `anon`.

SQL включает Row Level Security и запрещает посетителям прямой доступ ко всем таблицам и функциям. Не добавляйте публичные разрешения вручную и не отключайте RLS. Все запросы сайта проходят через защищённые серверные обработчики.

Отдельно включать Realtime, настраивать Supabase Auth, почту или OAuth **не нужно**. Используется автоматическое получение актуального снимка очереди через сервер сайта.

## 2. Загрузите проект на GitHub

Создайте репозиторий и загрузите исходники из этой папки. В корне репозитория должны находиться `package.json`, `package-lock.json`, `app`, `components`, `lib` и остальные файлы проекта — не вкладывайте весь проект ещё в одну папку без необходимости.

Не загружайте `node_modules`, `.next`, `.qa`, `.env.local` и другие файлы с секретами. `.gitignore` уже настроен. Файл `.env.example` содержит только названия настроек, его загружать можно.

## 3. Подключите GitHub к Vercel

1. В [Vercel](https://vercel.com/new) выберите **Add New → Project**, подключите GitHub и импортируйте репозиторий.
2. **Framework Preset:** Next.js. **Root Directory:** корень проекта.
3. **Node.js:** 24.x (версия также указана в `package.json`).
4. Стандартных настроек достаточно: установка `npm ci` или `npm install`, сборка `npm run build`, папка результата определяется Next.js автоматически. Не выбирайте статический экспорт и не задавайте `out` как Output Directory.
5. До первого Deploy добавьте переменные из следующего раздела. Если уже развернули сайт — добавьте их в **Settings → Environment Variables** и затем выполните **Deployments → Redeploy**.

## 4. Переменные окружения Vercel

Добавьте четыре обязательные переменные и, по желанию, название группы. Для основного сайта выберите окружение **Production**. Не добавляйте кавычки вокруг значений в интерфейсе Vercel.

| Название | Что вставить |
| --- | --- |
| `SUPABASE_URL` | Project URL из Supabase: `https://…supabase.co` |
| `SUPABASE_SECRET_KEY` | Secret key из Supabase: `sb_secret_…` |
| `ADMIN_PASSPHRASE` | Ваша собственная секретная фраза **от 4 символов**, лучше длинная и непредсказуемая; максимум 256 |
| `SESSION_SECRET` | Случайная строка для подписи сессий, сгенерированная командой ниже; минимум 32 символа |
| `GROUP_NAME` | Необязательно: например `ИВТ-231`. По умолчанию — «Наша группа» |

Сгенерируйте `SESSION_SECRET` у себя в терминале, в папке проекта:

```bash
node scripts/generate-secret.mjs
```

Команда выводит новый случайный секрет. Скопируйте его только в настройки Vercel (и локальный `.env.local`, если запускаете сайт на компьютере). Не используйте секретную фразу администратора вместо `SESSION_SECRET`. Ни одна из этих переменных не должна начинаться с `NEXT_PUBLIC_`.

Если нужны Preview-развёртывания, используйте для них отдельный тестовый проект Supabase и другие секреты: превью с теми же настройками будет работать с настоящей очередью.

## 5. Первый запуск

1. После Deploy откройте постоянную Production-ссылку сайта.
2. Внизу страницы нажмите **«Вход администратора»**.
3. Введите значение `ADMIN_PASSPHRASE`.
4. В блоке **«Управление»** укажите предмет, дату и время, при необходимости — аудиторию или примечание. Нажмите **«Открыть очередь»**.
5. Отправьте ссылку в беседу группы. Кнопка **«Пригласить группу»** копирует адрес.
6. Каждый студент вводит фамилию и имя, затем нажимает **«Встать в очередь»**.

Все даты и время пары вводятся и отображаются **по Москве (UTC+3)**. Открытие и завершение очереди выполняет администратор; время начала — информационное, автоматического сброса по расписанию нет.

## Правила очереди

- Кто записался раньше по порядку принятия запросов базой — стоит раньше. Одновременные действия сериализуются транзакционной блокировкой PostgreSQL.
- Повторное нажатие «Встать в очередь» не создаёт новую запись.
- Вышедший участник при повторной записи попадает в конец.
- Уже прошедший участник не может записаться снова на эту же пару.
- Одинаковые имена в одной очереди, включая прошедших, не допускаются. Пробелы и регистр нормализуются. Однофамильцы могут указать полное имя и отчество.
- Перенос с места 8 на 3 сдвигает промежуточных участников. Обмен 3 и 8 меняет только этих двоих.
- Если список изменился после открытия подтверждения, сервер отклонит устаревшее админское действие. Проверьте актуальные места и повторите его.
- При закрытой записи участники могут выйти; администратор всё ещё может править список и вручную добавлять людей.
- После завершения очередь доступна только для просмотра. Остаток очереди сохраняется вместе со списком прошедших.
- Максимум одновременно ожидающих — 200 человек. История выдаётся страницами по 20 пар, админский журнал показывает последние 100 событий выбранной пары. Остальные события остаются в базе.

## Вход по имени и смена устройства

Вход по имени работает на доверии: он не доказывает личность и не запрещает человеку назвать себя чужим именем. Список очереди и история видны любому, у кого есть ссылка. Править чужие места может только администратор.

Сессия участника хранится в подписанной HttpOnly-cookie, а очередь — в базе. Обновление страницы и закрытие браузера не теряют место. Очистка cookies, инкогнито или другой телефон создают новую сессию: старую запись нельзя присвоить, просто повторно введя её имя. В таком случае администратор может убрать старую запись, дать участнику записаться с нового устройства и вернуть нужное место.

Участник, добавленный администратором вручную, также не привязан к конкретному устройству; он видит себя в общем списке, а управляет этой записью администратор.

Админский пароль проверяется только на сервере. После **«Выйти из управления»** доступ пропадает в этом браузере; через 12 часов нужен новый вход. Для принудительного завершения **всех** старых сессий смените `SESSION_SECRET` и сделайте Redeploy. При утечке админской фразы смените и `ADMIN_PASSPHRASE`, и `SESSION_SECRET`.

## Локальный запуск с вашей базой

Установите Node.js 24 LTS. В терминале в папке проекта:

```bash
npm ci
```

Скопируйте `.env.example` в `.env.local` и заполните значения. Для PowerShell:

```powershell
Copy-Item .env.example .env.local
```

Затем:

```bash
npm run dev
```

Откройте `http://localhost:3000`. Это будет та же база, которая указана в `.env.local`; для экспериментов используйте отдельный проект Supabase.

Проверка production-сборки:

```bash
npm test
npm run typecheck
npm run build
npm start
```

Тесты `npm test` запускают отдельный PostgreSQL через PGlite, не подключаются к Supabase и не изменяют настоящие очереди. Они проверяют операции очереди, ограничения доступа, идемпотентность записи, архивирование, сессии и валидацию. В `tests/support` находится изолированный стенд для проверки HTTP и интерфейса; приложение его не импортирует.

## Если что-то не заработало

| Что видно | Что проверить |
| --- | --- |
| «Осталось подключить базу» | Все четыре обязательные переменные добавлены в Production; длина секретов достаточна; после изменений выполнен Redeploy. |
| «Нет связи с базой» | Project URL и **Secret key** относятся к одному проекту, SQL выполнен целиком, Data API включён, Supabase не приостановлен. Посмотрите также Function Logs в Vercel: сервер пишет код ошибки без секретов. |
| Неверная секретная фраза | Введите точное значение `ADMIN_PASSPHRASE`, учитывая пробелы и регистр. После изменения переменной нужен Redeploy. |
| Слишком много попыток | Сайт показывает, сколько подождать. Запись и выход имеют общий лимит: 2 действия за 5 секунд, 10 за минуту и 30 за 15 минут на участника. Админские изменения: 8 за 5 секунд и 45 за минуту на сессию. |

### Защита от спама

Счётчики хранятся в существующей таблице `rate_limits` в Supabase и атомарно обновляются функцией `take_rate_limit`. Они общие для всех экземпляров Vercel: перезагрузка страницы не обнуляет ограничения. Для этого обновления повторно выполнять SQL не нужно.

- Запись и выход используют один бюджет участника: 2 запроса за 5 секунд, 10 за минуту, 30 за 15 минут.
- Смена имени: 1 запрос за 5 секунд и 5 за минуту на существующую сессию. Регистрации и смены имени вместе: максимум 100 за 15 минут с IP.
- Изменения администратора: 8 за 5 секунд и 45 за минуту на сессию; дополнительно 90 за минуту с IP, чтобы повторный вход не сбрасывал весь бюджет.
- Вход администратора: 10 попыток за 15 минут с IP, включая успешные.
- Общий предел: 300 запросов действий за минуту с IP, включая некорректные и неавторизованные запросы с допустимым Origin. Он рассчитан с запасом для группы на общем Wi-Fi; личные лимиты участников независимы.

При превышении сервер возвращает HTTP 429 и `Retry-After`. Интерфейс выдерживает эту паузу перед следующей отправкой и не запрашивает дополнительное обновление при каждом отказе. Пауза указывается консервативно — полная длительность сработавшего окна; это не точное оставшееся время. Неудачные попытки тоже расходуют бюджет.

Ограничения IP используют заголовки доверенного прокси Vercel; при локальном запуске используется общий локальный бюджет. При переносе на другой хостинг нужно явно настроить получение доверенного IP. Автоматическое чтение очереди не расходует бюджет действий. Эта защита ограничивает спам изменений; она не заменяет сетевую защиту от DDoS и не подтверждает личность пользователя, который очищает cookies и меняет IP.
| Имя уже занято | Добавьте имя/отчество для однофамильцев или попросите админа восстановить запись после смены устройства. |
| Место не обновляется | Проверьте интернет. Скрытые вкладки не опрашивают базу. При возврате обновление происходит сразу, далее раз в 8 секунд. |
| Работает локально, но не на Vercel | Проверьте Production environment variables, настройки Next.js и Node.js 24.x. Нельзя размещать этот проект как набор статических файлов. |

## Бесплатный тариф и обслуживание

На момент подготовки проекта Supabase Free предоставляет 500 МБ базы и может приостановить проект после недели неактивности. Для небольшой учебной группы объём базы обычно достаточен, но бесплатные лимиты и условия провайдеры могут менять. После каникул проверьте статус проекта в Dashboard и при необходимости возобновите его.

Открытая вкладка делает примерно 450 запросов снимка в час. Для 30 участников, которые держат сайт открытым полтора часа, это около 20 250 запросов за пару. Следите за Usage на Vercel и Supabase, если сайт используется часто или несколькими группами. Автообновление останавливается в скрытой вкладке.

Для долгого хранения важной истории периодически сохраняйте резервную копию базы через инструменты Supabase. Ручной перезапуск или новый Deploy на Vercel не удаляет данные Supabase. Повторное выполнение `schema.sql` тоже не удаляет очереди, но будущие изменения структуры лучше оформлять отдельными миграциями.

Официальные справки: [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys), [Supabase Free](https://supabase.com/pricing), [развёртывание Next.js на Vercel](https://vercel.com/docs/frameworks/full-stack/nextjs), [переменные Vercel](https://vercel.com/docs/environment-variables).


### Время открытия записи

Поле «Открытие записи» задаётся по Москве. До этого момента участники видят очередь, но не могут записаться. После наступления времени запись становится доступна автоматически, без cron и фонового сервера; интерфейс получает новое состояние при обновлении (раз в 8 секунд). Проверка выполняется в PostgreSQL по времени сервера.

Ручное закрытие имеет приоритет: кнопка «Разрешить запись» снимает ручной запрет, но сохраняет ограничение по времени. Чтобы открыть раньше, измените время открытия. Перенос на будущее не удаляет участников; выход из очереди остаётся доступен. Администратор может добавлять людей вручную до открытия и при закрытой записи.

**Обновление существующего сайта:** выполните файл `supabase/migrations/20261009_registration_opening.sql` целиком в Supabase → SQL Editor → Run, затем разверните новую версию сайта. Данные сохраняются. Для новой базы используйте обычный `supabase/schema.sql` — он уже содержит изменения. Внутренние имена `starts_at` / `startsAt` сохранены для совместимости; существующие значения теперь означают открытие записи. При необходимости измените время активной очереди в панели администратора.


### Комментарии участников

Перед записью участник может добавить необязательный комментарий (до 200 символов), видимый всем под его именем, включая список прошедших и историю. При выходе и повторной записи можно указать новый комментарий.

Для существующей базы выполните `supabase/migrations/20261010_entry_comments.sql` в Supabase → SQL Editor → Run после предыдущих обновлений. Старые записи получат пустой комментарий, данные сохраняются. Для новой базы достаточно актуального `supabase/schema.sql`.
